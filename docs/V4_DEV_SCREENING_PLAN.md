# V4 DEV screening — candidate-set headroom

**Exploratory plan recorded after the V3 DEV non-promotion, before this diagnostic is computed.** This screen only reads the 200-video DEV cache for each codec. It will not read V1/V2 TEST, the completed V2 holdout, a V3/V4 holdout or `mc3_18`. It does **not** fit, freeze or validate a deployable policy.

For each DEV video and QP, form an **oracle** that may see the true correctness outcomes of both development analyzers. Keep only candidates that do not turn a correct `identity128` prediction into an incorrect one for either analyzer. From those, choose the smallest measured bpp, resolving ties by the original candidate order. The identity arm is always feasible. Report BD-rate/BD-accuracy and five-point curves versus identity using all 200 sources, plus candidate counts and the fraction of video/QP rows where a non-identity arm is feasible. This is an optimistic reference; selection uses labels and **must never be deployed or evaluated on a holdout**.

If this oracle leaves substantial rate–Top-1 headroom, the next development phase should improve the label-free risk selector rather than expanding pixel transforms immediately. If even this constrained oracle has little headroom, test new candidate transforms on DEV under a separate locked plan. The threshold for describing “substantial” is **not** a statistical gate; report exact values without choosing a winner from this diagnostic. Any V4 policy requires its own preregistration, freeze and fresh source-disjoint holdout. No result from the completed V2 holdout may enter V4 fitting or selection.
